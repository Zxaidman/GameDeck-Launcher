## GameDeck Android Community Code of Conduct

GameDeck is an open-source project built to create a better gaming experience for Android users.

The project welcomes contributors with different technical backgrounds, experience levels, cultures, and areas of expertise.

This document explains the behavior expected in GameDeck community spaces.

The goal is simple: people should be able to work on software without being harassed, intimidated, or treated disrespectfully.

---

## 1. Our Standard

Community members are expected to behave professionally and respectfully.

Examples of good participation include:

- discussing technical ideas directly
- asking questions without mocking people
- accepting different levels of experience
- explaining disagreements with evidence
- giving constructive criticism
- acknowledging mistakes
- giving credit for useful work
- respecting contributors' time
- assuming good faith unless there is evidence otherwise

You do not have to agree with another contributor.

You do need to treat them with respect.

---

## 2. Expected Behavior

### Be constructive

Focus criticism on the code, design, documentation, process, or idea rather than attacking the person.

Prefer:

> "This implementation adds a dependency we probably do not need and may make Android 10 support harder."

Instead of:

> "This is a terrible implementation."

### Be patient

Not everyone knows Android internals, Kotlin, Compose, Git, GitHub, or the same technical terminology.

GameDeck is intentionally welcoming to contributors who are learning.

### Be honest

Say when you are uncertain.

For example:

> "I tested this on one Samsung device running Android 14, but I do not know whether it works on Android 10."

That is more useful than pretending to know.

### Respect time

Avoid unnecessary demands on maintainers and contributors.

Reviews and technical discussions may take time.

---

## 3. Unacceptable Behavior

The following behavior is not acceptable in GameDeck community spaces:

- harassment
- discrimination
- threats
- stalking
- intimidation
- personal attacks
- deliberate humiliation
- sexual harassment
- unwanted sexual content
- hateful or demeaning language targeting protected characteristics
- publishing someone's private personal information without permission
- deliberate disruption of project infrastructure
- impersonation
- repeated bad-faith behavior after being asked to stop
- retaliation against someone who reports a legitimate concern
- intentionally introducing malicious code or backdoors
- deliberately submitting known unsafe code without disclosure

This list is not exhaustive. Behavior can violate this Code of Conduct even if it does not match a specific example above.

---

## 4. Technical Disagreement Is Allowed

GameDeck is a software project. Technical disagreement is expected.

You may challenge:

- the maintainer
- a pull request
- the PRD
- the architecture
- an API choice
- an implementation
- an AI-generated solution
- a roadmap decision

What matters is how the disagreement is expressed.

Use:

- evidence
- tests
- benchmarks
- Android documentation
- reproducible results
- reasoned arguments

Do not use:

- insults
- intimidation
- personal attacks
- harassment

A strong technical disagreement can improve the project.

---

## 5. AI-Assisted Development

AI coding tools are allowed.

People remain responsible for how they use them.

Examples of unacceptable behavior include:

- using AI to generate harassment
- submitting deliberately malicious AI-generated code
- intentionally flooding the repository with low-quality generated issues
- using AI-generated text to impersonate another contributor
- submitting copied proprietary material while falsely claiming it is original

AI-assisted contributions are expected to follow the same technical and community standards as human-written work.

See [`CONTRIBUTING.md`](CONTRIBUTING.md).

---

## 6. New Contributors Are Welcome

You do not need to be an Android expert to contribute.

Useful contributions can include:

- testing
- bug reports
- compatibility research
- documentation
- controller layouts
- skins
- UI feedback
- technical research
- code

Do not mock someone because they do not understand a concept yet.

Teach where practical.

---

## 7. Experienced Contributors

Experienced contributors are encouraged to share knowledge.

Expertise should not become a reason to:

- intimidate beginners
- dismiss questions
- dominate discussions
- make contributors afraid to report mistakes

A strong contributor helps make the project easier for others to understand.

---

## 8. Maintainer Responsibilities

Maintainers should:

- apply these standards consistently
- listen to legitimate concerns
- avoid personal retaliation
- explain significant moderation decisions when practical
- avoid using repository access as a threat
- protect contributors from harassment
- separate technical disagreement from personal conflict

Maintainers are not expected to accept every contribution.

They are expected to handle rejection respectfully.

---

## 9. Conflict Resolution

When practical, the preferred order is:

1. Direct technical discussion
2. Issue or pull-request discussion
3. Maintainer mediation
4. Private discussion if necessary
5. Moderation action when required

Not every disagreement needs formal intervention.

If the issue is technical, keep it technical.

If it becomes personal or abusive, moderation may be necessary.

---

## 10. Pull Request Conduct

Pull-request reviews should focus on:

- correctness
- maintainability
- architecture
- security
- testing
- compatibility
- project scope

Review comments should not focus on a contributor's intelligence, education, nationality, age, or personal background.

Prefer:

> "This will break Android 10 because this API was introduced later."

Not:

> "You clearly do not understand Android."

---

## 11. Issue and Discussion Conduct

Issues should describe real problems, requests, experiments, or proposals.

Do not intentionally create:

- spam
- duplicate floods
- harassment threads
- personal arguments
- malicious reports
- unrelated advertising

A disagreement with project direction is acceptable.

Turning that disagreement into repeated disruption is not.

---

## 12. Security Reports

Security researchers and contributors should be treated respectfully.

Do not retaliate against someone for reporting a legitimate security issue.

See [`SECURITY.md`](SECURITY.md) for security-reporting guidance.

Do not publicly post highly sensitive exploit details before reasonable remediation discussions have taken place.

---

## 13. Intellectual Property and Attribution

Respect the rights of other people and projects.

Do not submit:

- proprietary source code
- stolen assets
- unlicensed artwork
- leaked credentials
- confidential company material

When using third-party work, respect its license and attribution requirements.

See [`LICENSE`](LICENSE) and [`CONTRIBUTING.md`](CONTRIBUTING.md).

---

## 14. Commercial and Financial Discussions

GameDeck is currently community-first and is not being developed with a guaranteed profit model.

People may discuss:

- donations
- sponsorship
- hosting costs
- funding
- commercial possibilities

as long as the discussion remains respectful.

Financial disagreement is not an excuse for harassment.

Likewise, donors or sponsors do not automatically receive special authority over the project.

---

## 15. Enforcement

If a community member violates this Code of Conduct, maintainers may take appropriate action.

Possible actions include:

1. informal reminder
2. request to change behavior
3. moderation of a discussion
4. temporary restriction from community spaces
5. removal of comments or contributions where necessary
6. temporary suspension
7. permanent removal from project spaces

The response depends on:

- severity
- intent
- frequency
- impact
- whether the behavior stops when addressed
- whether there is a safety risk

Serious behavior may result in immediate action.

---

## 16. No Retaliation

Retaliation against someone who:

- reports harassment
- reports a security issue
- participates in moderation
- provides good-faith technical criticism

is not acceptable.

Good-faith reports should not result in punishment merely because someone disagrees with the report.

---

## 17. False Reports

Knowingly making false accusations to harm another contributor is also unacceptable.

There is an important distinction between:

- a good-faith report that turns out to be incorrect
- an intentionally fabricated accusation

The former should not be punished merely for being wrong.

---

## 18. Privacy

Do not publish another person's:

- home address
- phone number
- private email
- passwords
- private account information
- private conversations

without permission.

Public information a person intentionally shared publicly is different from exposing private information.

---

## 19. Scope

This Code of Conduct applies to official GameDeck project spaces, including where applicable:

- GitHub issues
- pull requests
- discussions
- repositories
- official chat spaces
- project meetings
- project-managed communication channels

Future official spaces should be covered unless explicitly stated otherwise.

---

## 20. Reporting Community Problems

If you experience or witness unacceptable behavior:

1. Preserve relevant evidence where appropriate.
2. Avoid escalating the conflict publicly.
3. Contact the project maintainer privately through the configured reporting channel.
4. Describe what happened and include links or screenshots when useful.

For security issues, use the process in [`SECURITY.md`](SECURITY.md).

---

## 21. Good-Faith Participation

GameDeck is intentionally built by people with different levels of knowledge.

Mistakes will happen.

AI-generated code will sometimes be wrong.

Android behavior will sometimes surprise us.

A contributor misunderstanding a technical detail is not a moral failure.

Correct the problem.

Explain the reason.

Improve the documentation when useful.

Move forward.

---

## 22. Final Principle

The standard for GameDeck community participation is simple:

> **Be someone you would be comfortable working with again.**

You can disagree strongly.

You can reject an idea.

You can challenge the maintainer.

You can point out serious technical mistakes.

You can say that a feature is impossible.

You can say that an AI-generated implementation is wrong.

Do those things honestly and respectfully.

That is good open-source collaboration.
